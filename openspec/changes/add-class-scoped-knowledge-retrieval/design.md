# Design

## Context

现有应用是一个使用 Flask、Flask-SQLAlchemy 和单个 SQLite 数据库的服务端渲染服务。每个用户都有一个权威的 `class_id`；资料列表、详情和文件访问已经根据登录用户确定班级范围。每份资料对应一个 `KnowledgeEntry`，其中保存经过标准化的完整 UTF-8 正文。当前 `/api/materials?q=` 使用 `ILIKE` 匹配标题和完整正文，随后返回正文前 180 个字符，因此既不能对内容片段进行相关性排序，也不能定位实际命中位置以供来源核验。

本变更需要保持离线运行方便，并适合以小型课程仓库形式提交。现有 SQLite 数据库和上传目录继续作为事实来源，不依赖远程模型或外部检索服务。

## Goals / Non-Goals

**Goals：**

- 增加具有确定性、支持行级来源定位的内容片段检索，同时保留现有服务端班级边界。
- 在当前 Flask 和 SQLite 技术栈内，使索引创建、回填、失败处理、测试和本地启动均可复现。
- 使检索结果契约与具体检索器充分解耦，以便未来的语义检索器仍能输出相同的来源字段。

**Non-Goals：**

- 生成回答、摘要、嵌入向量或对话回复。
- 在班级之间共享结果或增加多班级成员关系。
- 在本次迭代中运行独立数据库服务或下载嵌入模型。

## Decisions

### 使用 SQLite FTS5 作为检索索引

在同一个 SQLite 数据库中使用持久化 FTS5 虚拟表，并通过 FTS5 的 `bm25()` 对匹配结果排序。运行时能力检查确认可用后，使用 trigram 分词器，使中文文本和课程中常见的子串查询不依赖空格分词。用户查询在传入 `MATCH` 之前统一进行标准化和安全编码。

检索查询将 FTS 记录与关系型分块、资料记录连接，使用登录用户在服务端的班级限制 `knowledge_chunks.class_id`，先按相关性排序，再按稳定的分块标识排序。通过 FTS `snippet()` 或等价的应用层高亮方式生成命中位置附近的片段；返回的行号信息以关系型分块中保存的正文为准。

评估过的替代方案：

- **独立向量数据库：** 当查询与来源使用不同表达时，向量检索能够提升语义召回率，但它会引入第二套持久化系统、嵌入模型、模型来源与下载要求、向量维度和版本迁移，以及数据同步失败问题。对于本次要求的精确正文检索和离线课程提交，这些成本过高。未来的向量索引可以继续使用本设计的分块标识、班级过滤规则和来源契约。
- **继续使用 SQL `ILIKE`：** 该方案无需增加数据结构，但会扫描整篇正文，无法提供有效的相关性分数，也难以稳定实现命中位置摘要和索引健康状态。它仍适合现有资料列表过滤，但不适合作为独立知识检索接口。

### 使用确定性的关系型分块作为来源依据

新增关系型 `knowledge_chunks` 表，包含主键、确定性的 `chunk_id`、`knowledge_entry_id`、`material_id`、`class_id`、`start_line`、`end_line`、标准化正文和内容指纹。外键用于保持数据归属关系，并为 `class_id`、`material_id` 和 `knowledge_entry_id` 建立索引，以支持授权和维护查询。

按照行边界将标准化正文切分为有界窗口，目标大小约为 800–1200 个字符；长章节需要多个分块时，保留少量行重叠。除非单行本身超过最大长度，否则不单纯为了满足目标大小而切断一行；超长单行按确定性规则切分，同时保留原始行号。忽略只包含空白的窗口。根据知识条目标识、行号范围、片段序号和内容指纹生成 `chunk_id`，确保未变化的输入得到相同标识，而内容变化会产生新标识。

关系型分块是来源定位的权威数据。FTS 表保存分块标识、作为非索引元数据的班级和资料标识，以及可检索正文。检索结果根据资料标识生成详情和文件链接；现有接口仍会独立检查身份认证和班级归属。

### 增加独立的知识检索 API

新增 `GET /api/knowledge/search?q=<query>`，不修改现有 `/api/materials` 的响应契约。接口负责清理并校验查询，只从登录用户获取 `class_id`，调用检索服务并返回 `results` 数组。每条结果包含 `passage`、`material_title`、`material_id`、`chunk_id`、`start_line`、`end_line`、`detail_url` 和 `file_url`。

缺失或空白查询返回 `400` 和 `invalid_query`。授权范围内没有匹配结果时返回 `200` 和空数组。FTS 支持缺失、索引表缺失或损坏、运行时查询失败时，返回 `503` 和 `retrieval_unavailable`，不回退到未限定范围或结果不完整的查询。身份认证继续使用应用现有的 API 保护逻辑，并在检索前返回 `401`。

### 在同一事务中更新上传数据、分块和索引

扩展现有上传事务，在提交前创建资料、知识条目、确定性分块和 FTS 记录。关系型数据和 FTS 数据使用同一个 SQLite 连接，因此数据库变更会一起提交或回滚。文件仍在事务完成前写入；任何解析、分块、索引或提交失败都会删除该文件。只有全部数据库记录持久化成功后，API 才报告上传成功。

该方案延续现有上传流程的全有或全无契约，无需为这个课程规模的应用引入独立异步状态机。

### 提供幂等的初始化和回填流程

数据库初始化在确认所需的 FTS5 和分词器能力后，创建关系型分块表和 FTS5 虚拟表。新增管理命令，按照确定顺序处理已有知识条目。针对每个条目，在一个事务中替换其分块和 FTS 记录，报告处理成功数和失败数，并允许重复运行而不产生重复数据。

该命令不修改来源 `KnowledgeEntry.body`、资料归属或上传文件。单个条目处理失败时回滚该条目的变更，并在报告受影响来源后以失败状态退出，方便管理员修正问题后重新执行。

### 在现有界面中展示可溯源的检索结果

为保持兼容，保留现有资料列表及其简单过滤功能。新增独立的知识检索结果区域，展示命中位置附近的片段、来源标题和行号范围，并提供受保护的详情和文件入口。正文片段按文本渲染，而不作为可信 HTML；任何高亮均通过安全的 DOM 构造方式实现。

## Risks / Trade-offs

- [风险] 某些 SQLite 构建可能不包含 FTS5 或 trigram 分词器。→ 缓解措施：在初始化和测试中检查能力、记录受支持的运行环境，并返回 `retrieval_unavailable`，而不是静默降级。
- [风险] 与整篇正文的 `ILIKE` 相比，trigram 索引会占用更多数据库空间。→ 缓解措施：限制分块大小、忽略空分块，并将本设计用于课程规模的数据集。
- [风险] 重叠分块可能产生内容近似的重复结果。→ 缓解措施：使用较小重叠范围和稳定排序，并在同一资料的命中范围大量重叠时合并相邻结果。
- [风险] 不正确的查询构造可能触发 FTS 语法错误。→ 缓解措施：所有输入统一经过一个查询构造器，并测试标点、引号、中文文本和空白字符。
- [风险] 未来新增接口可能绕过班级过滤。→ 缓解措施：检索服务接收已认证用户，而非调用者提交的班级，并使用两个班级的数据测试 API、服务、详情和文件访问路径。
- [风险] 回填中断可能导致部分条目暂时没有索引。→ 缓解措施：保证每个条目独立原子提交，使命令具有幂等性，报告未完成项并支持安全重试。

## Migration Plan

1. 在数据库初始化流程中增加关系型分块表和 FTS5 虚拟表。
2. 部署带索引能力检查的检索服务和 API。
3. 运行幂等回填命令，并在开放检索界面前核对知识条目数和分块数。
4. 启用上传时的分块与索引创建，并验证上传失败回滚和上传后立即可检索。
5. 回滚时停用独立检索界面和 API，仅删除新增的分块表和 FTS 表；现有用户、资料、知识条目和上传文件保持不变。
